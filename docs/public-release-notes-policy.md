# 公开版更新说明边界

官网更新历史、Sparkle 更新说明和两个官网镜像使用同一套公开文案。它们服务于用户，不承担工程日志、测试报告或内部复盘的职责。

## 写什么

- 每个版本先用一句话说明这次变得哪里更好
- 保留 2–5 条用户能感知、能理解的变化
- 使用用户看到的名称和结果，不解释内部实现路径
- 需要用户采取动作时，直接写清步骤和影响

## 不写什么

- 自动化测试数量、构建过程和发布流水线
- 未公开版本如何合并、内部排期和临时版本号
- 竞态、线程、缓存、框架、API 等实现细节
- 调试过程、根因推演、竞品痕迹和内部人员信息
- 为显得丰富而拆开的细碎修复；可以收束为「其他细节优化」

## 不能模糊处理的内容

以下信息必须明确公开，不能为了文案克制而隐藏：

- 数据丢失、错误修改或隐私泄露风险
- 安全问题以及用户需要采取的防护或更新动作
- 破坏性变化、功能移除和不兼容变化
- 新增权限、系统版本或硬件限制
- 已知限制以及会影响用户判断的重要事实

0.4.8 的马赛克位置问题是这个边界的基准案例：内部实现原因可以省略，但旧截图可能没有遮住敏感信息、用户应重新检查，必须保留。

## 发布前检查

1. 官网更新历史与对应的 `notes/Chock-<version>.html` 表达一致。
2. 主站与大陆站使用同一份静态文件，不单独改文案。
3. 自动测试检查公开页面没有测试数量、内部根因或未发布版本说明。
4. 涉及隐私、安全、兼容性和必要用户动作的条目经过人工确认。

完整测试证据、根因和发布过程继续保存在产品内部文档，不复制到公开页面。
