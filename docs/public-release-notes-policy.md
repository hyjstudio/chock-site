# 公开版更新说明边界

官网更新历史、Sparkle 更新说明和两个官网镜像使用同一套公开文案。它们服务于用户，不承担工程日志、测试报告或内部复盘的职责。

## 写什么

- 当前版本保留版本号、发布日期和一句简短说明；0.5.7 只写「做了些许优化。」
- 历史版本保留一句事实摘要和 1–4 条用户能感知的变化，让功能演进与版本脉络可追溯
- 使用用户看到的名称和结果，不解释内部实现路径、技术原因或排障过程
- 更新历史与对应的 `notes/Chock-<version>.html` 使用同一组公开事实

## 不写什么

- 自动化测试数量、构建过程和发布流水线
- 未公开版本如何合并、内部排期和临时版本号
- 竞态、线程、缓存、框架、API、服务器与签名流程等实现细节
- 具体 bug 复现步骤、错误方向、敏感场景和处置指导
- 调试过程、根因推演、竞品痕迹和内部人员信息
- 「全面升级」「更稳定更流畅」等没有事实信息的口号
- 为显得丰富而拆开的细碎修复；可以合并为一条用户能理解的结果

## 不能丢失的历史层级

- 每个已发布版本都保留至少一项非空说明，不能只剩版本号和日期
- 不同版本保留各自的功能事实，不能全部替换成同一句模糊文案
- 重要的功能加入、兼容性、试用与授权变化应保留；内部机制和敏感细节不公开
- 安全、隐私、破坏性变化或必要用户动作按需要通过独立通知、帮助页面或应用内提示处理

完整影响、根因、处置和验证证据继续保留在内部 release evidence。

## 发布前检查

1. 官网更新历史与对应的 `notes/Chock-<version>.html` 使用同一组公开事实。
2. 主站与大陆站使用同一份静态文件，不单独改文案。
3. 自动测试检查每个历史版本有非空说明，且没有内部根因、敏感场景或未发布版本说明。
4. 人工检查最新版主次清楚、历史版本可快速扫读，没有空泛口号和重复文案。
5. 涉及隐私、安全、兼容性和必要用户动作时，确认已有合适的独立沟通入口。

完整测试证据、根因和发布过程继续保存在产品内部文档，不复制到公开页面。
